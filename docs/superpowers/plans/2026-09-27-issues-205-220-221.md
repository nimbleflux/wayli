## Diagnosis (verified)

**#205 — Address lookup.** Three stacked causes:
1. `11 Beecroft Street, Huskisson` does not exist in OpenStreetMap. Verified via OSM API bbox `150.660,-35.052,150.682,-35.030`: Beecroft Street exists as an untagged residential way; the only 7 addressed objects in town are 9/8/20 Currambene St, 11 **Dent** St, 64-66 Owen St, 9 Hawke St, 4 Woollamia Rd. No geocoder built on OSM data can return it. (What resolves on openstreetmap.org is the street itself or 11 Dent St.)
2. The deployed Pelias index (`pelias-20260901-000017`, 225M docs) is broken beyond the data gap: **0 street-layer docs**, and **no document carries the `phrase` field** (ES-verified samples of venue/address/locality docs) while the API's coarse/admin matching routes through the placeholder service which matches on `phrase`. Result: searching "Nowra"/"Huskisson"/"Sydney" returns only venues — even the maintainer's "fill out your city" workaround fails.
3. Interpolation data exists on the geonode (`/srv/geonode/interpolation`, Jan 2026) but the monthly build never refreshes it, and the OSM source data has no interpolation ways there anyway.

**#205 — Blue circle.** `account-settings/+page.svelte:1233` stores manual coordinates as `{ display_name: "lat, lng", coordinates: { lat, lng } }`, but the only renderer of the home circle — `location-data/+page.svelte` `normalizeHomeAddress()` (lines 627–651) — recognizes only the adapter shape (`location.{lat,lon}`) and the raw Pelias shape (flat `lat/lon`), so it returns `null` and `drawExclusionZones()` (line 743) never draws. Introduced by commit 9fb8cdcf (PR #206) which added the third shape on the write side only.

**#205 — Trip detection with coordinates.** Works, but degraded: `trip-detection.service.ts` `isPointInLocation()` (line 551) accepts a point as "home" if it is in the same city **or** within 50 m of the stored coordinates. Manual coordinates keep the 50 m check (coordinates survive `parseLocation()`, lines 1222–1241) but city matching is skipped because the manual shape has no `address.city`. Reverse-geocoding the coordinates at save time restores full behavior.

**#220 — Activity detection.** Detection is a 6-state HMM (`stationary|walking|cycling|car|train|airplane`) duplicated in `web/src/lib/services/transport-mode/` and `fluxbase/jobs/_shared/services/transport-mode/` ("Update both together" contract). Speed dominates emissions; 5–35 km/h lands in cycling's band, so boating reads as cycling. No water signal exists anywhere. Available water signals, verified: reverse geocoding open water returns zero results and the job persists failures with `geocoding_status: 'failed'` + a `retryable` flag (`geojson-converter.ts:91`); Valhalla edge `use` types already include `'ferry' | 'rail_ferry'` (unused); Pelias/OSM addendum tags (`waterway`, `natural=water`, …) flow into `tracker_data.geocode` already.

**#221 — FIT import.** `fit-decoder.ts:823–828` reads session fields 0/1 (`event`, `event_type`) as sport/sub_sport; per the FIT profile they are fields **5** and **6**. The sample file `260816195715.fit` (Bryton, road ride): `event=9` → `SPORT_MAP[9] = 'american_football'`, `event_type=1` → `SUB_SPORT_MAP[1] = 'treadmill'` → fitness row shows "CYCLING · TREADMILL" (sport label was rescued by the `IMPLAUSIBLE_SPORTS` → power-data fallback at lines 254–278). The existing test (`web/tests/unit/fit-decoder.test.ts:126–162`) asserts the buggy values. Note: the repo sample file is NOT the issue reporter's file — the fix is the general field-number correction, not file-specific tuning.

- [ ] **Step 1:** In `PRIOR` add `boat: 0.05, swimming: 0.05`. After the existing boost blocks, add:

```ts
const waterStrong = f.waterFraction >= 0.5 && f.onWater;
if (mode === 'boat' && waterStrong) s *= 3.5;
if (mode === 'swimming' && waterStrong && f.speed <= 8) s *= 4.0;
// Suppress the land modes boat/swimming compete with, only under strong water
// evidence and only at speeds where the water mode is physically plausible.
```

### Task D2: Find and fix the missing street layer

**Files:** build script + possibly importer/schema version pins (same files as D1).

**Facts:** the live index has 0 `layer:street` docs while addresses (174M) and venues (45M) imported fine; the mapping is `dynamic: strict`. Leading hypothesis: the Sep 1 build's importer version vs schema mismatch rejects street docs at bulk time (build only checks `doc_count > 1000`, so rejection was silent). The repo now pins `pelias/openstreetmap:v8.5.2` + `pelias/schema:v9.1.0`.

- [ ] **Step 1:** During the rebuild, capture the importer's stderr/bulk-error counts (add `2>&1 | tee /srv/build/state/osm-import.log` and a grep for `index_rejected`/bulk errors that `die`s above a threshold).
- [ ] **Step 2:** If street docs are still 0 after a fresh import with the pinned versions: create a scratch index with the prod mapping, bulk-index one synthetic street doc matching what the importer emits, and read the rejection reason; adjust the version pairing (schema/importer) accordingly — never edit the schema by hand.
- [ ] **Step 3:** Verification: `curl '127.0.0.1:9200/pelias/_search?q=layer:street&size=0'` shows millions of hits on the new index before alias switch.

### Task D3: Monthly interpolation build + post-build verification probes

**Files:**
- Modify: `geonode/build/docker-compose.build.yml` (add an `interpolation-build` service: `pelias/interpolation` in build mode over the planet PBF, output to `/srv/build/interpolation`)
- Modify: `geonode/build/build-pelias-monthly.sh` (run it; ship `address.db` + `street.db` to `/srv/geonode/interpolation/` in `transfer-on-geonode.sh`/`ship-to-geonode.sh`; restart the interpolation container)
- Create: `geonode/build/verify-pelias-index.sh`

**verify-pelias-index.sh** (run after import, before alias switch; exit 1 on any failure):
1. ES layer agg: `street > 1M`, `locality > 1M`, `venue > 1M`, `address > 100M`;
2. sample 100 random docs: ≥90% have a `phrase` field (or: placeholder admin probe works — see D1 decision);
3. API probes through the tunnel against the NEW index: `/v1/search?text=George Street Sydney&layers=street` returns a street; `/v1/search?text=Nowra&layers=coarse` returns a locality; `/v1/reverse` on open water (`-35.05,150.72`) returns empty;
4. interpolation service answers `/interpolation/extract?lat=-35.04&lon=150.67` style probe.

- [ ] Wire the script into `build-pelias-monthly.sh` before the alias switch (die on failure — this is the guard that would have caught all of this).
